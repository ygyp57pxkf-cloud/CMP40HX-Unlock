# 2026-09-14 启动停滞诊断

结论：14:51失败轮次的原生UEFI Shell经LoadImage成功加载，但StartImage返回Device Error（EFI_DEVICE_ERROR，x64数值0x8000000000000007）。RefindPlus暂停6秒后返回自己的Main Menu，没有将控制权交回固件或直接启动Windows。日志证明应用当时仍在执行错误处理，不证明整机已经硬死；之后菜单是否响应键盘未实测。30秒等待未完整执行，失败阶段早于本轮算力解锁。

虽然文案使用While Loading，RefindPlus launch_efi.c中该日志实际在gBS->StartImage返回后记录，不能读成LoadImage文件加载失败。昨天09-13 11:38的26r13m3840.log已有同样错误；昨天成功不能替代失败回退验收，这一旧失败线索应纳入后续分析。

## 原因范围

已确认：自动默认项确实执行；失败在Shell子程序执行/初始化范围；错误处理返回菜单，缺少无人值守失败转Windows路径。

优先假设：EDK2 Shell早期文本控制台调用返回设备错误。对应edk2-stable202602 Shell.c进入UefiMain后先调用ConOut->ClearScreen，失败直接返回Status；此时尚未处理startup.nsh的connect/30秒，也尚未靠-noconsolein绕过控制台输入。ConsoleLoggerInstall及其他早期协议初始化也有错误路径，因此ClearScreen仍是候选，不能在缺少函数级日志时宣称它已被证明。

显示器断电/未连接、冷启动控制台状态可作为对照，但尚待用户确认两次实体显示器状态。成功与失败日志都显示GOP=NO和同样UEFI版本不一致警告，不能单独把这些字段当根因。社区定向检索没有找到可直接套用的同平台修复；RefindPlus #214是Apple/iMac显示问题，不作为本机修复依据。

本次ESP回读中Trace/Shell/原算力EFI/脚本/配置/微软文件全部与昨日指纹一致；ESP还有约55MiB空间。没有重新复制、改注册表、重置显卡或改启动顺序的证据需要。

## 应整改的两件事

1. 可靠失败回退：前置管理器对Shell StartImage错误最多做一次有界重试，再直接启动微软Windows；不要回无限等待的菜单，也不要反复调用旧失败算力EFI。Windows第一后备项本身不能替代管理器内部失败处理。
2. Shell早期定位：在原生EFI层保存ClearScreen、ConsoleLoggerInstall和后续初始化返回码，测试不依赖实体显示器的控制台路径。若需等待/连接设备，位置应在Shell启动之前；再加startup.nsh内部等待对这次错误无帮助。

这两项目前是由证据确定的下一步设计，尚未编译/部署新的EFI。当前成功配置保持；不要把诊断结论写成已根治。若再次停在RefindPlus菜单，可选Windows recovery；无响应时按既有现场指引关机后从主板选Windows Boot Manager。不会要求远程WOL承担强制断电恢复。
